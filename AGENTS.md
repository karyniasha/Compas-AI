# AGENTS.md — правила работы с проектом «Компас»

## Контекст и приоритеты
«Компас» — конкурсный MVP для SK Challenge 2026: адаптивный ИИ-наставник по образовательным и карьерным решениям. Цель — подготовить устойчивую, проверяемую демонстрацию к 31 октября 2026 года. Не переписывать существующее приложение с нуля.

Перед изменениями прочитай `docs/HANDOFF.md`, `docs/PROJECT_BRIEF.md`, `docs/REQUIREMENTS.md`, `docs/TECH_SPEC.md`, `docs/TASKS.md`, `docs/DECISIONS.md`, затем `README.md`, `app.py`, `kompas/core.py` и тесты. При расхождениях фактическое поведение кода проверяй тестами; документацию обновляй вслед за изменениями.

## Технологии
- Python 3.11, Streamlit, `unittest`.
- В текущей версии `app.py` — интерфейс, `kompas/core.py` — сценарии и проверка ответов, `tests/` — тесты.
- SQLite и JSON/SQLite для памяти и базы знаний — планируемые компоненты, **не считай их реализованными**.
- Доступа к LLM API пока нет: локальный тестовый режим должен работать полностью без ключа. LLM впоследствии подключается через изолированный адаптер, без зависимости бизнес-логики от конкретного провайдера.
- Не вводи новые зависимости или фреймворки без реальной необходимости.

## Продуктовые требования
- Главная персона: Георгий, 17 лет, Саратов, интересуется историей; рассматривает СПбГУ, СГУ, РГГУ и МГУ. Его бюджет, баллы, год поступления и предпочтения заранее неизвестны и должны выясняться в диалоге.
- Три сценария: выбор вуза (`history`), первая стажировка (`internship`), адаптация на работе (`onboarding`).
- ИИ должен помогать принимать самостоятельное решение, а не навязывать «лучший вуз».
- Отсутствие данных — это «неизвестно», а не ноль и не основание исключить альтернативу.
- Факты о вузах, экзаменах, проходных баллах и расходах показывай только с проверяемым URL, годом и датой проверки. Не переносить условия 2026 года на 2027 или 2028 без подтверждения.
- Держи раздельно информационный режим, тренажёр, память ошибок и экспорт; отсутствие LLM всегда обозначай пользователю явно.
- Не собирай чувствительные сведения без необходимости; перед сохранением пользовательских данных предусматривай согласие и удаление.

## Порядок работы
1. Перед крупной задачей коротко сформулируй минимальный план и критерии готовности.
2. Изучи существующий код и вноси **небольшие изменения**; сохраняй существующие интерфейсы, если нет обоснованной причины их менять.
3. Для исправленной ошибки или новой функции добавляй или обновляй тесты.
4. Запускай тесты и сообщай результат; не объявляй функцию работающей без проверки.
5. Покажи краткое резюме: изменённые файлы, что проверено, что не проверено, известные ограничения.
6. Обновляй `docs/TASKS.md`, `docs/DECISIONS.md` и релевантные требования после значимых изменений.
7. Не выполняй `git push`, публикацию, удаление больших частей проекта или разрушительные команды без явного разрешения автора. Не коммить секреты, `.env`, `.venv`, локальные персональные данные.

## Команды Windows PowerShell (из корня репозитория)
```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m streamlit run app.py
```
Если виртуальное окружение отсутствует:
```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## Первая техническая задача после подготовки среды
Провести аудит MVP 0.1, сопоставить `docs/REQUIREMENTS.md` с кодом, выделить минимальные изменения до MVP 0.2. Первый приоритет — модель проверяемых источников и информационный режим, работающие без LLM API. Не добавляй неподтверждённые цифры о вузах ради демонстрации.
